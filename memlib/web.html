为什么要有它

Agent 每天都在产生经验，但下一次会话什么都不记得。这个项目要补的不是「存」，而是「找」： 把散在各处的记忆、知识和历史会话，变成一条命令就能查到的东西。

类型例子没有它的时候
协作记忆「提交前先跑 lint，别等 CI 挂」散在各 project 目录，跨项目不共享，每次重新纠偏
领域知识踩坑页、SOP、改动记录攒在笔记目录里，只能靠人翻
历史会话「上次那个缓存问题怎么绕的」埋在几千个 jsonl 里，grep 不动

定位：统一检索层，不是又一个笔记系统

  • 事实源原样、原地不动：Markdown 和会话文件该在哪还在哪，依赖现有路径的笔记软件和流水线都不受影响。
  • 索引是派生物：.index/memory.db 随时能删掉用 mem index --full 重建。
  • 写入要过人眼：模型起草的记忆一律先进 staging，审核后才合入——写错的记忆比没有记忆更糟。
  • 全本地、离线：库里是业务内容和会话原文，不能出网。

刻意不做的事

不做知识图谱、不做自动摘要、不做常驻服务、不做多机同步。一个 CLI，冷启动不到 1 秒出结果，够用。这个看板也是按需启动的；它不直接写库，审核页的操作一律转调 mem 命令。

三层事实源 块数为当前索引实时值

L1 协作记忆

—

用户偏好、纠偏、项目约束、外部资源指针。memory/ 下的 Markdown，人工审核后合入； 索引页 MEMORY.md 是唯一在开场注入上下文的文件。

L2 领域知识

—

知识库、踩坑、SOP、改动记录、协作复盘。原地只读索引你在 config.json 的 sources 里配置的笔记目录，不搬家—— 搬家会打断其他依赖现路径的工具。

L3 历史会话

—

Claude Code / Codex 的会话。默认按「一问一答」回合切分进索引；也可以从 sources 去掉会话源，只靠 mem review 把会话起草成候选记忆、人审后合入 L1（取舍见下方「关键设计 7」）。 会话结束时只记一个指针，原文始终留在 transcript 里。

关键设计：为什么这么定

1. 必须两条腿

精确标识（表名、工单号、类名如 RetryTemplate）：嵌入模型没见过，向量基本是噪声，只能靠关键词。

自然语言问法（「这个接口为什么偶尔超时」）：原文可能一个字都对不上，只能靠语义。

砍掉任何一条，都有一整类查询直接报废。

2. 中文用 trigram，而且必须逐字滑动

FTS5 默认分词器不切中文，整句一个词等于不可用。trigram 每 3 字切一刀，不依赖词典，业务黑话照样命中。

"日志检索超时重试"
stride=3: 日志检 / 索超时 / 重试      ← 跨词碎片，命中恒为 0
stride=1: 日志检 / 志检索 / 检索超 / 索超时 / 超时重 / 时重试
          ✓ 真实词片一定在候选里

候选变多后再用 df 过滤：零命中的丢掉、出现在 25% 以上块里的丢掉，剩下按稀有度取前 12 个。随库内容自适应，不用维护停用词表。

3. 减全局均值：语义腿能不能用的分水岭

bge 类模型有「各向异性」：所有向量挤在一个窄锥里。实测不处理时全库相似度落在 0.64~0.72，最相关和毫不相关只差 0.05。

索引时算一次全库平均向量，检索时两边都减掉再归一化，窄锥被拉开，排序才有意义。成本只有两次减法。

4. RRF：只看名次，不看分数

bm25 没有上界，余弦在 -1~1，两个分数不可比，直接相加没有意义。RRF 扔掉分数，只用名次：Σ 1/(60 + 名次)。

块  关键词名次  语义名次   得分
A   第 1        没捞到     1/61        = 0.0164
B   第 5        第 3       1/65 + 1/63 = 0.0313  ← 两条腿都认，反超
C   没捞到      第 1       1/61        = 0.0164

5. 按标题切块，标题拼进嵌入文本

检索单位是块不是文件：一篇 5000 字的踩坑页里可能记了七八件事。块太大，向量被平均成四不像；太小又丢上下文。

一个只写着「改成 3 就行了」的块没有可检索的语义；嵌入时拼上 缓存不失效踩坑 / 排查 / 并发度，向量才落在正确的位置。展示仍用原文。

6. 分层保底席位

L1 只占全库约 — 的块，等权排序下几乎永远进不了 top-k——一条精确的记忆会被几十条沾边的知识页压掉（会话层停用前更严重）。

所以没限定层时给 L1/L2 留几个席位，席位要么关键词命中、要么语义分过阈值（0.30），避免凑数。

7. 会话层：索引还是只提炼

会话增长最快。实测一台机器用了一个多月后，会话占到全库约八成的块，其中大头是固定的自动化任务模板、 <task-notification>、<skill> 等系统注入，以及「继续」「是的」这类无信息量的回合。 现有过滤只按会话来源筛，不看内容，挡不住这些。

可以选择不索引会话：有复用价值的结论本来就该进 L1 并过人审，mem review 已经在做；代价是没被提炼的结论查不到，只能按 session id 回 transcript 找。

当前规模与设计边界 实时

什么时候该推翻这套设计

  • 块数超过 10 万：numpy 暴力检索开始吃力，换 sqlite-vec 或 HNSW（配置里的 index.backend）。
  • 需要多机共享：SQLite 单文件 + 同步会冲突，得上服务端。
  • 需要结构化查询（「上周所有关于 XX 的改动」）：现在只有全文和语义两条腿，元数据都在 meta_json 里没建索引。

已知边界

  • 没有时间衰减：三年前和昨天的结论一视同仁，L2 靠 verified_at / status: stale 人工兜底。
  • 只按文档去重：同一件事在 L1 记一遍、L2 又写一遍，仍会各占一个结果位。
  • 查不到会话原文：没被提炼成记忆的结论检索不到。
  • 没有重排：top-8 里通常有 1~2 条语义腿捞来的擦边球。
  • 增量索引按 mtime：touch 会触发重新嵌入，内容改了但 mtime 没变会漏；有疑虑就 --full。
  • L2 是线索不是事实：与当前代码、配置、数据库冲突时以现状为准。
